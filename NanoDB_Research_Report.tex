\begin{abstract}
Building a database engine from scratch is one of the most demanding, and most
rewarding, ways to understand what actually happens beneath the abstractions that
developers take for granted every day. This paper documents the design,
implementation, and empirical evaluation of \NanoDB, a functional
mini relational database engine written entirely in C++ with no Standard Template
Library (STL) containers. Every core component was implemented by hand: the
buffer pool, the LRU eviction cache, the hash map catalog, the AVL index, the
SQL expression parser, and the multi table join optimizer. The engine runs on
100,000 real records from the TPC H benchmark~\cite{tpch2023}, evaluates complex
WHERE expressions through a Shunting Yard parser operating on a custom stack, and
routes multi table joins using a graph based MST algorithm. Empirically, the AVL
tree index was roughly 69 times faster than a sequential scan on 20,000 records,
and at 100,000 records the speedup reached $879\times$. The buffer pool correctly
handled 4,950 LRU evictions under a 50 page memory constraint with zero memory
errors. This paper details the reasoning behind each design decision, provides
mathematical proofs of component efficiency, and presents measured results from
the live running system.
\end{abstract}

\section{Introduction}

There is a real difference between knowing how to use a database and
understanding how one works. A developer who writes SQL queries every day may
never think about what happens inside the engine when that query lands as a raw
character string: how the WHERE clause gets broken apart into executable
operations, how the planner decides which table to read first, or why a
differently ordered join can shift query time from a few milliseconds to several
minutes. These are not obscure edge cases. They are the core of what a database
engine does, and most programmers never see them directly.

The \NanoDB\ project was built to change that, at least personally. The central
constraint is simple: no STL. No \code{std::vector}, no \code{std::map}, no
\code{std::stack}, no \code{std::sort}. Every data structure is built from raw
arrays and pointers. This restriction is frustrating at first, but it turns out
to be an unusually effective way to learn. When you write your own doubly linked
list and watch it handle thousands of LRU evictions in microseconds, while an
equivalent array would require millions of element shifts, the performance
argument for linked structures stops being something you read about and becomes
something you have seen work in practice. The same thing happens with AVL
rotations, operator precedence stacks, and heap based scheduling: implementing
them yourself, and then watching them run correctly on real data, builds a kind
of intuition that is hard to get any other way.

The resulting system is a working relational engine. It reads records from TPC H
benchmark files~\cite{tpch2023} and stores them in a paged binary format on
disk. It indexes primary keys using a self balancing AVL tree~\cite{cormen2022},
evaluates SQL WHERE clauses through a Shunting Yard parser on a custom stack,
routes multi table joins through a graph based cost optimizer, and handles
high priority administrative queries through a binary max heap scheduler. This
paper documents how each component was designed, proves its theoretical
complexity, and presents empirical benchmarks from the actual running system.

\section{Related Work}

\NanoDB\ draws on several active lines of research in storage systems, indexing,
and query optimization. This section situates the design decisions within that
broader context, highlighting where existing work directly informed the
implementation and where the constraints of a from scratch project led to
different choices than a production system might make.

\subsection{Buffer Pool and Memory Management}

The idea of managing a fixed pool of memory pages explicitly, rather than letting
the OS handle it through memory mapped I/O, has been debated in the systems
community for years. Crotty et al.~\cite{crotty2022} make a strong case for the
explicit approach, showing that mmap based engines give up fine grained control
over what happens when memory runs short and can suffer from unpredictable latency
spikes as a result. Their argument resonated directly with the \NanoDB\ design:
every page eviction in this engine is a deliberate decision made by the buffer
pool, not an opaque OS event.

Neumann and Freitag's Umbra system~\cite{neumann2020} takes this further,
demonstrating that a carefully engineered disk based engine can reach performance
levels close to in memory systems. The key insight from Umbra is that the buffer
pool architecture itself is not the bottleneck; what matters is how predictably
and efficiently it can be managed. That principle guided the choice of a
doubly linked list combined with a hash map for the LRU cache in \NanoDB, since
both eviction and promotion need to be $O(1)$ for the overhead to remain
negligible relative to actual disk I/O.

\subsection{Indexing Structures}

The AVL tree has a long history in algorithms literature~\cite{cormen2022} and
remains one of the cleaner choices for a primary key index when correctness and
predictability matter more than squeezing out extra throughput. The strict height
invariantno two subtrees at any node can differ by more than one levelkeeps
lookup time at $O(\log N)$ regardless of insertion order, which is exactly the
kind of worst case guarantee that matters for a project where the data comes from
a benchmark and insertion order is not under our control.

The learned index line of work, particularly ALEX by Ding et
al.~\cite{ding2020}, is a genuinely interesting alternative. ALEX fits a
piecewise linear model to the key distribution and can outperform B tree variants
on read heavy workloads with relatively stable data. The tradeoff is complexity:
the model needs to be updated as data changes, and its performance degrades if the
key distribution shifts in unexpected ways. For \NanoDB, where inserts and
updates happen alongside reads and where the primary goal is to understand the
mechanics rather than maximize throughput, the AVL tree's four well defined
rotation cases and straightforward invariant were a better fit.

\subsection{Query Optimization}

The join ordering problem is as old as relational databases themselves, and it
remains an area of active research. Marcus et al.~\cite{marcus2021} introduced
Bao, a system that uses Thompson sampling to nudge the underlying query optimizer
away from historically bad plan choices. Bao does not replace the optimizer
entirely but learns, over time, which plan ``hints'' tend to produce better
outcomes on a given workload. The results on benchmarks like JOB and TPC H are
substantial.

\NanoDB's join optimizer takes a much simpler approach: it models tables as graph
nodes, join costs as edge weights, and applies Kruskal's MST
algorithm~\cite{cormen2022} to find the ordering with the smallest total estimated
intermediate result. For two or three tables this works well and can be computed
essentially instantly. The more sophisticated machinery of Bao would become
relevant once the join set grows large enough that simple cost proxies are no
longer reliable, but at the scale of this project the MST approach produces
correct orderings in every tested case.

Leis et al.~\cite{leis2023} examine a related problem at the scheduling level,
showing that the order in which queries are executed in an analytical workload
meaningfully affects end to end throughput and tail latency. \NanoDB\ handles
this through a binary max heap scheduler, a lightweight but practically important
mechanism that ensures administrative operations always preempt background reads.

\section{System Architecture}

\NanoDB\ is structured as a layered pipeline, where each layer has a single
well defined responsibility and communicates with the layers above and below it
through narrow interfaces. Fig.~\ref{fig:arch} gives a conceptual view of the
stack.

At the bottom, the \textbf{Pager} handles raw binary I/O, reading and writing
fixed size pages to disk. It delegates residency tracking entirely to the
\textbf{LRU Cache}, which decides which pages stay in memory and which get
evicted when the buffer pool fills. Above the storage layer, the \textbf{Schema
Engine} provides a polymorphic type system built around \code{DataType},
\code{IntType}, \code{FloatType}, and \code{StringType}. Virtual comparison
operators on these classes let the rest of the engine evaluate expressions without
any explicit type dispatch codethe right comparison just happens through
virtual dispatch. The \textbf{Hash Map Catalog} maps table names to their
registered metadata in $O(1)$ expected time using the djb2 hash function with
separate chaining for collision resolution.

The \textbf{Query Parser} sits above the catalog. It tokenizes SQL like input and
converts WHERE clauses to postfix form using the Shunting Yard algorithm. The
\textbf{Executor} takes over from there: it resolves table references, picks
between indexed and sequential scan access paths based on whether an AVL index
exists, evaluates the postfix expression row by row using the custom stack, and
calls into the MST join optimizer when more than one table is involved. Finally,
the \textbf{Priority Queue Scheduler} wraps the whole pipeline, ensuring that
ADMIN prefixed queries always get processed before ordinary reads regardless of
when they were submitted.

\section{Memory Management: Buffer Pool and LRU Cache}

The buffer pool is one of those components that seems straightforward until you
actually build it. The idea is simple enoughkeep a fixed number of pages in
memory and evict the least recently used one when the pool fillsbut getting the
eviction logic right without any unpredictable latency requires some care in the
choice of data structures. This section describes how \NanoDB\ handles it.

\subsection{Design}

A database cannot load an entire dataset into RAM at once, especially at the
TPC H scale used here. The buffer pool provides the abstraction that makes this
manageable: at any point, only a bounded number of pages are resident in memory,
and when the pool is full and a new page is needed, the page that has gone longest
without being touched is written to disk and its slot is reused. This is the LRU
policy, and it works well in practice because database access patterns tend to
exhibit temporal localityrecently accessed data is likely to be accessed again
soon.

The point made by Crotty et al.~\cite{crotty2022} about OS memory mapped I/O is
worth emphasizing here. If you let the OS manage page residency through mmap, the
database loses visibility into when evictions happen. That means it cannot
guarantee dirty pages are flushed before they leave memory, and it is exposed to
whatever eviction heuristic the kernel chooses, which may not match the query
workload's access pattern at all. Handling eviction explicitly, as \NanoDB\ does,
keeps the engine in control of its own memory.

\subsection{Implementation}

\NanoDB's LRU cache is built from two structures working together. A
doubly linked list maintains the access order: the head of the list is the most
recently accessed page, the tail is the least recently accessed. Every time a
page is accessed, it is unlinked from its current position and moved to the head
in $O(1)$ time by adjusting four pointers (predecessor's next, successor's prev,
old head's prev, and the node's own next and prev). When the pool is full and a
page needs to be evicted, the tail node is removed in $O(1)$ timeno scanning,
no shifting.

The list alone is not enough, because checking whether a particular page is
already resident would require traversing it linearly. A hand built hash map
solves this: it maps each page ID to a direct pointer to the corresponding list
node, so residency checks and cache hits are $O(1)$ expected time. The djb2
hash function distributes integer page IDs well across buckets, keeping chain
lengths short in practice.

\subsection{Complexity Analysis}

Let $C$ be the buffer pool capacity in pages and $B$ the number of hash map
buckets.

\textbf{Space:} $O(C + B)$. Each of the $C$ resident pages has one list node and
one hash map entry. The bucket array adds $O(B)$ overhead.

\textbf{Lookup, promotion, and eviction:} all $O(1)$ expected. Hash map lookup
gives a direct pointer to the list node; list relinking touches a constant number
of pointers regardless of pool size; tail eviction is a single pointer
adjustment. This matches the performance model Neumann and Freitag demonstrated
for their Umbra buffer pool~\cite{neumann2020}, where $O(1)$ eviction overhead
is essential to keeping disk I/O as the dominant cost rather than CPU side
bookkeeping.

\section{Indexing: AVL Tree}

Without some form of index, every lookup in a large table degrades to a linear
scan. At 20,000 customer records that is manageable; at 100,000 it becomes
noticeably slow; at millions of records it becomes completely impractical. \NanoDB\
addresses this with a self balancing AVL tree on the primary key of each table,
and the benchmark results in Section~\ref{sec:eval} show how much difference it
makes in practice.

\subsection{The Problem with Sequential Scans}

A query like \code{WHERE c\_custkey == 10000} directed at a 20,000 row customer
table has no choice but to examine every row in order if there is no index. On
average it will find the match halfway through, meaning roughly 10,000
comparisons. In the worst casethe target key is the last one in the
fileit is all 20,000. For a single lookup this is already noticeable; for a
workload that issues thousands of point queries, the cumulative cost is severe.
An index avoids this by precomputing a mapping from key values to row IDs, so a
single lookup touches only the nodes on a path from root to leaf.

\subsection{Implementation}

\NanoDB\ builds an AVL tree over the integer primary key of every registered
table at load time. Each node stores four things: the key value, the row ID for
that key, a height field used to maintain the balance invariant, and left and
right child pointers. Insertions walk down the tree to find the correct position,
place the new node, and then update heights on the way back up. If the insertion
makes any subtree's left and right heights differ by more than one, a rotation
corrects it. There are four cases: LL (single right rotation), RR (single left
rotation), LR (left right double rotation), and RL (right left double rotation).
Each rotation is a fixed sequence of pointer reassignments and height updates
taking $O(1)$ time~\cite{cormen2022}, so the overall insertion cost stays $O(\log
N)$.

One design decision worth noting is that the AVL tree is built entirely in memory
and is not persisted directly. On shutdown, the raw records are written to disk,
and on reload the tree is rebuilt by re inserting every primary key. This keeps
the persistence logic simple and means the tree is always consistent with the
on disk data without any additional synchronization logic.

\subsection{Complexity Analysis}

The height bound on an AVL tree follows from the recurrence $N_h = 1 + N_{h 1} +
N_{h 2}$, where $N_h$ is the minimum number of nodes in a valid AVL tree of
height $h$. Since this recurrence grows at least as fast as the Fibonacci
sequence, the height satisfies $h < 1.44\,\log_2(N+2)$ for a tree with $N$
nodes~\cite{cormen2022}. In practice the constant factor is small enough that the
difference between an AVL tree and a perfectly balanced binary search tree is
rarely visible at workload scales below tens of millions of nodes.

\textbf{Space:} $\Theta(N)$. Each of the $N$ keys occupies one node with a
constant number of fields.

\textbf{Search and insertion:} $O(\log N)$ worst case. The contrast with learned
indexes like ALEX~\cite{ding2020} is worth noting: ALEX can achieve better lookup
times on static, read heavy workloads by fitting a model to the key distribution,
but requires retraining when data changes and performs poorly if the distribution
is non uniform or shifts over time. For a write capable engine with benchmark data
inserted in unpredictable order, the AVL tree's deterministic guarantee is the
right trade off.

\section{Query Parsing and Expression Evaluation}

Turning a raw SQL WHERE clause into something a machine can actually evaluate
requires more work than it might look like from the outside. The string
\code{(c\_acctbal > 5000 AND c\_mktsegment == "BUILDING") OR c\_nationkey == 15}
has to be broken into tokens, have its operator precedence resolved correctly, and
then be evaluated row by row against live data. \NanoDB\ handles this in three
stages: tokenization, Shunting Yard conversion to postfix form, and stack based
evaluation.

\subsection{Tokenization}

The tokenizer scans the WHERE clause a character at a time, consuming whitespace
and grouping the remaining characters into typed tokens. It recognizes column
names (sequences of letters, digits, and underscores beginning with a letter),
integer and floating point literals, quoted string literals, the five arithmetic
operators (\code{+}, \code{ }, \code{*}, \code{/}, \code{\%}), six comparison
operators (\code{==}, \code{!=}, \code{<}, \code{>}, \code{<=}, \code{>=}), the
logical operators \code{AND} and \code{OR}, and matching parentheses. Each token
carries a type tag and its raw text, which is enough information for the
Shunting Yard stage to process it correctly.

\subsection{Shunting Yard Conversion}

The Shunting Yard algorithm, originally described by Dijkstra, converts the
infix token stream to postfix (Reverse Polish Notation) form using two
auxiliary structures: an output queue and an operator stack. The rules are
straightforward: operand tokens (column names, literals) go directly to the
output queue; operator tokens are compared to whatever is currently on top of the
stack, and any operators with higher or equal precedence are popped to the output
before the new operator is pushed; right parentheses trigger pops until the
matching left parenthesis is reached and discarded.

The precedence levels assigned in \NanoDB\ are: OR\,=\,1, AND\,=\,2,
comparisons\,=\,3, addition and subtraction\,=\,4, multiplication, division, and
modulo\,=\,5. This ordering ensures, for example, that \code{a + b > c AND d}
is correctly parsed as \code{((a + b) > c) AND d} without requiring the user to
write explicit parentheses. The algorithm's correctness is established
in~\cite{cormen2022}.

\subsection{Evaluation}

At query time the postfix token stream is evaluated row by row using a custom
\code{Stack<DataType*>}. For each token: if it is a column reference, the
corresponding cell from the current row is looked up and cloned onto the stack;
if it is a literal, a fresh \code{DataType} object of the appropriate type is
allocated and pushed; if it is a binary operator, two operands are popped, the
operation is applied through virtual dispatch on the \code{DataType} base class,
and the result is pushed back. When all tokens are processed, the single value
remaining on the stack is the row's evaluation resultnon zero means the row
passes the filter.

Using virtual dispatch here is what allows the evaluator to handle mixed type
expressions without any explicit type checking in the evaluation loop. Whether the
operands are integers, floats, or strings, the correct comparison or arithmetic
operation is selected automatically by the vtable.

\subsection{Complexity}

Each of the three stagestokenization, Shunting Yard conversion, and postfix
evaluationruns in $O(T)$ time, where $T$ is the number of tokens in the
expression. Every token is processed a constant number of times: once during
tokenization, at most twice during Shunting Yard (pushed onto the stack and
popped to the output), and once during evaluation. Total parsing and evaluation
cost is therefore linear in expression length, regardless of the depth of
nesting or number of operators.

\section{Query Optimizer and Scheduling}

Two distinct optimization problems live under this section's heading. The first
is structural: in what order should a multi table query join its relations? The
second is temporal: when multiple queries are waiting, which one should run next?
\NanoDB\ addresses each with a different algorithm, and the two operate
independently of each other.

\subsection{Join Ordering via MST}

When a query touches more than one table, the order in which the joins are
performed matters enormously. Joining two large tables first produces a large
intermediate result that then has to be joined with the third table; joining
a small table with a large one first, if the join condition is selective enough,
can keep intermediate sizes manageable. Without any optimizer, the engine would
just join tables left to right in whatever order they appear in the query, which
is often not the best choice.

\NanoDB\ uses a graph based cost proxy to avoid this. Each table in the query
becomes a node in an undirected graph. For every pair of tables that can be
joined, an edge is added with weight equal to the product of the two tables' row
countsa rough but reasonable estimate of the intermediate result size that a
naive join would produce. Kruskal's MST algorithm~\cite{cormen2022} then finds
the spanning tree with the minimum total edge weight, and the join order follows
the tree structure. For the three table case (customer, orders, lineitem) with
counts of 20,000, 30,000, and 50,000 rows respectively, the MST correctly
identifies customer orders as the preferred first join (cost $6\times10^8$)
before joining with lineitem, rather than starting with the more expensive
orders lineitem join (cost $1.5\times10^9$).

For two or three tables the full graph has at most three edges and the MST is
found immediately. The approach would need to be replaced with a proper dynamic
programming enumerator for larger join sets, as noted in the future work of
systems like Bao~\cite{marcus2021}, but at the current scale it produces correct
orderings in every tested case.

\subsection{Priority Queue Scheduling}

Queries enter the system through a binary max heap priority queue rather than a
simple FIFO queue. Standard SELECT queries receive priority 0, and any query
prefixed with the \code{ADMIN} keyword receives priority 100. The heap property
guarantees that the highest priority query at the front of the queue is always
selected next, regardless of when it was submitted or how many lower priority
queries are waiting behind it.

This maps directly to the scheduling concern studied by Leis et
al.~\cite{leis2023}: in an analytical workload, allowing low priority background
reads to block time sensitive administrative operations is a source of
unpredictable tail latency. The priority queue mechanism eliminates that. In the
demo test, a single ADMIN INSERT submitted after fifty SELECT queries was
dequeued and executed first, confirming correct heap behaviour.

Heap insert and extract max both run in $O(\log N)$ time for a queue of depth
$N$, which is negligible compared to any actual I/O cost.

\section{Empirical Evaluation}
\label{sec:eval}

Theory and implementation together tell most of the story, but the numbers are
what make the design choices concrete. This section presents benchmark results
from the actual running system, organized around the two performance critical
componentsthe AVL index and the LRU cachefollowed by a summary of the
functional correctness tests.

\subsection{Experimental Setup}

The engine was compiled with \code{g++  std=c++17  O2} on Windows 11. All
timing measurements used the C++ \code{std::chrono::high\_resolution\_clock} at
nanosecond resolution, averaged over five runs to reduce noise. TPC H
data~\cite{tpch2023} was loaded at the full project scale: 20,000 customers,
30,000 orders, and 50,000 line items, for a combined record count of 100,000
across the three tables.

\subsection{Index vs.\ Sequential Scan}

To isolate the indexing benefit, a synthetic benchmark was run at three table
sizes: 1,000, 10,000, and 100,000 rows. For each size, the benchmark measured
the time to retrieve the last inserted key under both access paths: a sequential
scan (worst case, since the target is at the end of the file) and the AVL index.

69.4 fold speedup. For a single query this saves about 130 microseconds; across a
workload of thousands of point queries, the cumulative savings would be measured
in seconds.

the stress test deliberately removes that locality to verify that the eviction
mechanism itself is correct under continuous pressure. Because each eviction is an
$O(1)$ linked list operation, the CPU overhead of the entire cache management
layer was negligible compared to the cost of the simulated disk writes throughout
all test scenarios.

\subsection{Functional Validation: Demo Test Cases}

Beyond the performance benchmarks, seven functional test cases were run to verify
correctness across the full range of engine features.

\textbf{A  Parser:} The expression \code{(c\_acctbal > 5000 AND c\_mktsegment
== "BUILDING") OR c\_nationkey == 15} was tokenized, converted to postfix form,
and evaluated correctly against the customer table. The token sequence was logged
to confirm correct operator ordering.

\textbf{B  Index Optimizer:} Sequential and indexed lookup times for a
specific \code{c\_custkey} in the 20,000 row customer table were printed to the
console side by side, showing the 69.4 fold speedup in real time.

\textbf{C  Join Optimizer:} A three table join over customer (20K rows),
orders (30K rows), and lineitem (50K rows) ran after the MST optimizer printed
its chosen join path. The optimizer selected the customer orders join first,
consistent with the minimum cost analysis.

\textbf{D  Memory Stress:} A 50 page pool processed 5,000 distinct page
accesses in sequence and printed exactly 4,950 evictions, matching $\max(0,
5000   50) = 4950$ analytically.

\textbf{E  Priority Queue:} Fifty SELECT queries were submitted, then a single
ADMIN INSERT was added to the queue. The INSERT was dequeued and executed first,
confirming correct max heap behaviour.

\textbf{F  Complex Expression:} The query \code{((o\_totalprice * 1.5) >
100000 AND (o\_custkey \% 2 == 0)) OR (o\_orderstatus != "O")} exercised
arithmetic, modulo, comparisons, AND, OR, and nested parentheses in a single
expression. It evaluated correctly across all tested rows.

\textbf{G  Persistence:} Five customer records were inserted and serialized to
disk. After a full engine restart with \code{ reload}, all five records were
recovered and the AVL indexes were rebuilt correctly, confirming that the
paged binary format is stable across process boundaries.

\section{Conclusion}

\NanoDB\ ended up being a genuinely working relational database engine. It stores
and queries 100,000 TPC H records, evaluates complex SQL like expressions with
correct operator precedence, routes multi table joins through a cost optimizer,
manages a fixed memory pool through explicit LRU eviction, and persists data
safely across restarts. Nothing in the implementation relies on STL containers.

The benchmarks confirmed what the theory predicted. At 100,000 records, index
lookups were $879\times$ faster than sequential scans. Thousands of LRU evictions
ran without a single memory error. The MST optimizer correctly ordered a
three table join. The priority queue preempted fifty waiting reads to execute a
single administrative insert. These are not surprising resultsthe algorithms
are well understoodbut seeing the numbers come out of a system you built
yourself carries a different kind of weight than reading about them.

The deeper value of the project is harder to quantify but probably more durable.
Writing an LRU cache from scratch and watching the $O(1)$ pointer relinking handle
thousands of evictions where an array would need millions of shifts makes the
design principle feel real in a way no textbook explanation quite achieves. The
same is true for every other component. Understanding \emph{why} a data structure
is the right choice for a problem, as opposed to just knowing \emph{that} it is,
comes from building it and seeing it work.

Several directions remain open. Extending the AVL index to support range queries
through in order traversal would make the engine useful for a wider class of
predicates. Replacing the MST join optimizer with a proper dynamic programming
approach, along the lines of what systems like Bao~\cite{marcus2021} sit on top
of, would handle larger join sets correctly. And it would be worth experimenting
with whether a learned index structure like ALEX~\cite{ding2020} could replace the
AVL tree for read heavy scans once the engine has a stable enough data
distribution to make model training worthwhile.
